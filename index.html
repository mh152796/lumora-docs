Lumora Documentation

Welcome to the documentation for Lumora, an online academy platform made of three projects: a Flutter mobile app for learners (Android and iOS), a NestJS + PostgreSQL backend API, and a Next.js admin panel. Learners browse and buy courses, watch lessons, take quizzes and timed live exams, and earn certificates. You run everything from the admin panel.

What is in this package:
  • Flutter-App/ — the learner app (Android and iOS).
  • Backend/ — the NestJS + PostgreSQL API.
  • Admin-Panel/ — the Next.js admin panel.
  • Documentation/ — this guide.
Accounts you need before you start: your own Firebase project (the app ships placeholder google-services.json and GoogleService-Info.plist files that you replace with your own, section 4) and, if you sell through Google Play, your own RevenueCat account (the app uses the RevenueCat SDK purchases_flutter for Google Play purchases; RevenueCat has its own pricing and terms, section 11). Full list: Third-Party Services and Costs.

Setting up for the first time? Start with the backend (section 13), then the admin panel (section 14), then come back to the app (sections 1–12). The app needs a running backend to show anything.

Feature Walkthrough

A plain-language tour of what the app does, so you can find your way around before touching any code. Nothing in this section needs programming knowledge; the technical setup starts at section 1.

First launch

  • The app shows a short intro and the sign-in screen. Learners sign in with email and password or with Google, or create an account.
  • If you turn on learning preferences, the app then asks for the learner's topics, goal, level and languages, and builds a personal Home screen from the answers.
  • The app name, logo, brand colours, languages, payment methods and feature switches all come from your backend, so the app looks like your academy without a rebuild.

The main tabs

  • Home: banners and course rails (Hot picks, For you, Because you enrolled in, categories, top courses) in the order you set in the admin panel.
  • Search: search with filters (category, level, price, rating, instructor) and sorting, plus recent and trending searches.
  • Exams: upcoming, live and finished live exams with results and the leaderboard.
  • My Learning: the learner's courses with progress, certificates and offline downloads.
  • Account: profile, purchase history, wishlist, notifications, settings, help and legal pages.

Buying a course

  • Learners add courses or bundles to the cart, or tap Buy now for one course. At checkout they can apply a coupon.
  • The Payment page lists only the methods that the academy turned on and that every course in the cart accepts: Stripe, Flutterwave, Razorpay (hosted web checkout) and, for a single course on Android, Google Play.
  • With Google Play, the app shows the price Google charges in the learner's own currency, with a note that it can differ from the course price.
  • The course unlocks as soon as the backend confirms the payment. A receipt appears and the order is listed in Purchase history.

Learning

  • Lessons can be videos (MP4, or adaptive streaming with Bunny Stream), articles, PDF documents and quizzes. Progress is saved as the learner watches.
  • Each lesson has notes, questions and answers, and course announcements. Allowed lessons can be downloaded for offline use.
  • Quizzes support pictures and maths equations. Live exams run at a set time with a timer, then show results and ranks.
  • When a course is complete, the learner confirms the name to print and gets a certificate with a QR verification page. It can be downloaded as a PDF, shared as an image or added to LinkedIn.

Languages and appearance

  • The app ships in English, Bengali, Hindi, Arabic (right-to-left) and Spanish. You choose which ones learners can pick and the default language.
  • Learners can switch between light and dark mode. Your brand colours apply to both.

What you control from the admin panel

  • Courses (details, pricing, curriculum, quiz builder, publishing), bundles, categories and live exams.
  • The app's Home screen: banners and course rails, with impressions, clicks and revenue per rail.
  • Learners, instructors, certificates and your team with staff roles.
  • Orders and refunds, coupons, sale campaigns, Google Play store products and the revenue report.
  • Push notifications, review moderation, course questions and FAQ.
  • Settings: branding, business mode, currency, languages, payment methods, legal pages, email, media, video hosting, feature switches, maintenance mode and the minimum app version.

A tour of the admin panel with screenshots is in section 14.

How the Pieces Connect (Architecture)

Lumora is three projects around one backend. Only the backend talks to the database and holds secrets; the app and the admin panel never see a database password or a payment secret key.

ConnectionWhat happens
App → BackendEvery request goes to your API_BASE_URL with the X-Tenant header (your academy slug). Signed-in learners also send their Lumora access token in Authorization: Bearer. The backend issues and refreshes these tokens itself.
App → Firebase → BackendFor Google sign-in, the app gets a Google ID token and the backend checks it against GOOGLE_CLIENT_IDS. The app also registers its push token with the backend after sign-in.
Admin panel → BackendStaff sign in with email and password. The admin panel's own server keeps the session in HttpOnly cookies and calls the backend's /console/* routes. The browser never calls the backend directly.
Backend → PostgreSQLAll data lives here. Only the backend connects. Money steps (order, payment, refund) each run in one database transaction.
Backend → S3 storage / Bunny StreamThe admin panel uploads files straight to your bucket with short-lived upload links from the backend. Learners get short-lived signed links to lesson files, or stream videos from Bunny Stream.
App → Gateway → BackendFor web checkout, the backend opens a hosted payment page (Stripe, Flutterwave or Razorpay) and the app shows it. The gateway's webhook tells the backend the result; the backend checks it with the gateway before it unlocks the course.
App ↔ Google Play / RevenueCat → BackendFor Google Play, the backend opens a pending order, the app buys the store product through RevenueCat, and the backend reads the purchase back from RevenueCat before it unlocks the course. RevenueCat's webhook also reports late purchases and refunds.
Backend → Firebase Cloud MessagingPush notifications (from the admin panel, exam reminders, announcements) are sent by the backend with your Firebase service account.
Scheduler → BackendA cron call to /internal/cron/minute every minute runs exam results, reminders, push delivery, missed-payment checks and cleanup.

4. Firebase Setup

Firebase provides push notifications, crash reports and the Google part of Google sign-in. Email and password accounts, sessions and everything else are handled by your own backend, not by Firebase.

You must use your own Firebase project. The package ships placeholder Firebase files with values such as YOUR_ANDROID_API_KEY and your-firebase-project-id. They let the project compile, but push notifications, crash reports and Google sign-in will not work until you replace them:
  • Flutter-App/android/app/google-services.json
  • Flutter-App/ios/Runner/GoogleService-Info.plist
No Firebase project of ours is included, so your app never connects to our accounts.

Step 1: Create a Firebase project

  • Open the Firebase console and click Create a project. Enter a name and accept the terms.
  • Choose whether to enable Gemini and Google Analytics (Lumora needs neither), then click Create project.

Step 2: Add the Android app

  • In the project, click Add app > Android and enter your package name from section 3.
  • Download google-services.json and replace Flutter-App/android/app/google-services.json.
  • Add your SHA-1 and SHA-256 fingerprints now if you use Google sign-in (section 5), then download the file again.

Step 3: Add the iOS app (optional)

  • Click Add app > Apple, enter your bundle ID, download GoogleService-Info.plist and drag it into Runner/ in Xcode (tick "Copy items if needed"), replacing the placeholder.

Step 4: Turn on what you use

  • Crashlytics: open Run > Crashlytics and click Enable. Release builds upload their R8 mapping file automatically.
  • Google sign-in: open Build > Authentication > Sign-in method and enable Google (details in section 5).

Step 5: Service account for the backend

The backend sends push notifications with a Firebase service account: Project settings > Service accounts > Generate new private key. Put the whole JSON on one line in the backend's FCM_SERVICE_ACCOUNT_JSON (section 13). Keep this file secret; it is never part of the app.

5. Google Sign-In and Push Notifications

Firebase is your own project, under your own Google account and Google's terms (see Third-Party Services). Every key below comes from your account.

Google sign-in

The app asks Google for an ID token and sends it to your backend (POST /auth/google), which checks it and starts a normal Lumora session.

  • Fingerprints: Google sign-in only works for builds signed with a key registered in Firebase. In Project settings > Your apps > Android, click Add fingerprint and add the SHA-1 and SHA-256 of every key you use: 
    # the shared debug key (debug and profile builds)
keytool -list -v -keystore android/app/lumora-debug.jks -alias lumora -storepass lumora-debug

# your upload key (section 12)
keytool -list -v -keystore /path/to/your/upload-keystore.jks -alias upload
    Also add the Play App Signing key from Play Console (Test and release > App integrity > App signing): Google re-signs downloads from Play with it. Download google-services.json again afterwards.
  • Web client ID: after enabling Google in Authentication, copy the Web client ID (in google-services.json it is the oauth_client entry with "client_type": 3). Put it in the app's GOOGLE_WEB_CLIENT_ID (section 8) and in the backend's GOOGLE_CLIENT_IDS. The two must match, or the backend refuses the sign-in.
  • iOS: add the REVERSED_CLIENT_ID from GoogleService-Info.plist as a URL scheme in Xcode (Runner > Info > URL Types).

Push notifications

  • Android: Cloud Messaging works with google-services.json alone. On Android 13 and newer the app asks for the notification permission after sign-in.
  • iOS: upload an APNs key to Firebase (Project settings > Cloud Messaging > Apple app configuration), and add the Push Notifications and Background Modes > Remote notifications capabilities in Xcode. Test on a real device; the simulator cannot receive push.
  • Backend: set FCM_SERVICE_ACCOUNT_JSON (section 4, step 5) and make sure the minute cron runs (section 13); push is delivered by the cron.
  • Every install subscribes to the topic all, so the admin panel's "all learners" notifications need no token list. Notifications to one course's learners or to inactive learners use the device tokens the app registers after sign-in.
  • Tapping a notification opens the in-app Notifications inbox.

9. Languages

The app ships five languages: English (en), Bengali (bn), Hindi (hi), Arabic (ar, right-to-left) and Spanish (es). In the admin panel (Settings > General > Languages) you choose which ones learners can pick and which one a new install starts with. The admin panel itself is in English.

What a language file looks like

Each language is one file in lib/l10n/: app_en.arb, app_bn.arb and so on. Every key has the same name in every file. A plain text and a text with a value inside:

{
  "@@locale": "en",
  "commonRetry": "Retry",
  "payStoreSubtitle": "Pay with your {store} account, in your local currency",
  "@payStoreSubtitle": {
    "placeholders": { "store": { "type": "String" } }
  }
}

Add a language (example: French)

  • Copy lib/l10n/app_en.arb to lib/l10n/app_fr.arb, change "@@locale": "en" to "@@locale": "fr" and translate every value (not the keys, not the {placeholders}): 
    {
  "@@locale": "fr",
  "commonRetry": "Réessayer",
  "payStoreSubtitle": "Payez avec votre compte {store}, dans votre devise locale"
}
  • Add the language to the picker list in lib/src/core/localization/locale_cubit.dart: 
    static const List<AppLanguage> supported = [
  AppLanguage('en', 'English', 'English'),
  // ...
  AppLanguage('fr', 'French', 'Français'),
];
  • Generate the code and run the app: 
    flutter gen-l10n
flutter run --dart-define-from-file=config/app_config.json
  • Turn the new language on in the admin panel (Settings > General > Languages). Course titles and descriptions are your own content; you write them in the admin panel.

Remove a language

  • The quick way: turn it off in the admin panel. Learners no longer see it.
  • To remove it from the app: delete its app_xx.arb file and its line in locale_cubit.dart, then run flutter gen-l10n.

Step 3: Turn it on

  • Switch the gateway on in Settings > Payments. The app's Payment page lists it at once.

  • Refunds: open the order in Orders and refund all or some items. The refund goes back through the gateway, and the learner loses access to the refunded course.

Payment simulator (local testing only)

Never turn this on in production. While PAYMENT_SIMULATOR_ENABLED=true, any signed-in learner can mark their own order as paid without paying, for every gateway that has no keys.

What it does. The simulator lets a developer test the purchase flow (order, access to the course, My Learning, certificates) before any payment gateway is set up. With it on, the backend accepts a gateway that has no keys, and an order on such a gateway can be settled with one API call instead of a real payment. Orders on a gateway that has keys, and all Google Play / App Store orders, are always paid for real; the simulator refuses them. It is a backend tool for developers: the learner app has no simulator button.

How to turn it on for local testing:

  1. On your own computer, set PAYMENT_SIMULATOR_ENABLED=true in the backend's .env and restart the backend. The log shows a warning: PAYMENT_SIMULATOR_ENABLED=true: orders on a gateway without keys can be marked paid without money changing hands.
  2. Create an order as a signed-in learner (POST /checkout/orders, section 17). Its answer contains "payment": { "action": "simulate", "endpoint": "/checkout/orders/<id>/simulate-payment" }.
  3. Settle it with the learner's token: 
    curl -X POST http://localhost:3000/checkout/orders/ORDER_ID/simulate-payment \
  -H "Authorization: Bearer LEARNER_ACCESS_TOKEN" -H "X-Tenant: your-academy-slug" \
  -H "Content-Type: application/json" -d '{"outcome":"success"}'
    "outcome": "success" marks the order paid and unlocks the courses; "failed" closes it and gives the coupon back.

How to confirm it is off before you go live:

  1. Open the backend's production .env (or your host's environment variables, for example on Vercel) and check that PAYMENT_SIMULATOR_ENABLED is false or not there at all. It is off unless it is exactly true.
  2. Restart the backend and read the start-up log (pm2 logs lumora-backend). With the simulator on, a production server logs an error: ... Turn it off before taking real orders. No such line means it is off.
  3. Optional check: call POST /checkout/orders/ANY_ORDER_ID/simulate-payment as a learner. With the simulator off the answer is 403 with Payment simulator is disabled.
Safety rules built in: nothing in a webhook body is trusted; the backend reads the payment again from the provider. Each event is processed once. If a webhook never arrives, the minute cron asks the provider about open payments, so orders still settle. Money that arrives for an order that can no longer take it is refunded automatically, or flagged on the order for you.

11. Google Play In-App Purchases (RevenueCat)

On Android, learners can buy a course with Google Play. Stores sell from a catalogue of products with prices set per country, so a course bought this way is paid with a store product (for example course_999 at USD 9.99) instead of the course's own price. Many courses can share one product. RevenueCat connects the app to Google Play and confirms every purchase to your backend.

Your accounts, your costs: you need your own Google Play Developer account, your own products in Play Console and your own RevenueCat account. Google keeps a service fee on every purchase; RevenueCat is free up to a monthly revenue limit and then takes a share.
Android only is tested. Steps 1–5 below are for Google Play, which is tested end to end. App Store (iOS) purchases use the same code path but have not been tested; they are described separately in App Store purchases (untested) at the end of this section. Do not assume iOS works the same until you have tested it yourself.

Step 1: Create the products in Play Console

  • Upload a build of the app to a testing track first (internal testing is enough): Play Console only allows products for an app that has the BILLING permission, which the app already declares.
  • Open Monetize with Play > Products > One-time products and create a few products at different prices, for example course_299, course_499, course_999, course_1499, course_1999. Set each price and activate it. Google converts the price for each country.

Step 2: Set up RevenueCat

  • Create a project at app.revenuecat.com and add a Google Play app with your package name. Upload a Google Play service account key as RevenueCat's setup asks, so it can read your purchases.
  • Import the products (Product catalog > Products) and keep them consumable.
  • Copy two keys from Project settings > API keys: the app's public SDK key (goog_…) and a secret API key (sk_…, version 1).

Step 3: Enter the keys

In the admin panel open Settings > Payments > App stores > Google Play and enter:

FieldValueEnvironment variable
Secret keyRevenueCat secret API key (sk_…). Server onlyREVENUECAT_SECRET_KEY
SDK keyRevenueCat public SDK key (goog_…). Sent to the appREVENUECAT_GOOGLE_SDK_KEY
Webhook authorizationA long random string you make up (step 4)REVENUECAT_WEBHOOK_AUTH

Saving keys in the admin panel needs the backend's SETTINGS_ENCRYPTION_KEY; the environment variables work without it. Switch Google Play on. Its display name and logo (shown on the app's Payment page) can be changed on the same screen.

Step 4: Add the webhook

In RevenueCat open Integrations > Webhooks > Add:

  • Webhook URL: https://api.your-domain.com/webhooks/revenuecat/<your academy slug> (shown in the admin panel). One URL serves both stores.
  • Authorization header value: the same random string as the Webhook authorization field.

The webhook settles a purchase when the app closed before it could confirm, and removes access when a purchase is refunded from the store.

Step 5: Add the store products in the admin panel

  • Open Sales > Store products and add each product ID exactly as in Play Console, with its reference price in your academy currency (the price in the store's base country). The reference price is only used to match products to courses and for your reports; Google decides what each buyer pays.
  • Products are archived, never deleted, so past orders keep their product.

Payment methods per course

  • Every course accepts all payment methods that are switched on, including ones you turn on later. Open a course's Pricing step to remove a method for that course (for example, Google Play only, or web checkout only) and add it back any time.
  • Google Play uses the store product whose reference price is closest to the course price (a tie takes the cheaper one), so it follows price changes automatically. Pick a different product on the Pricing step to override it.
  • A cart only offers the methods that every course in it accepts. Google Play is offered for a single course at a time; coupons and sale prices do not apply to store purchases.

Testing

  • Add your Google account as a licence tester (Play Console > Settings > License testing) and install the app from the testing track. Test purchases are not charged.
  • The Payment page shows Google's price in the tester's currency. After paying, the course unlocks within a few seconds. A purchase appears in RevenueCat's dashboard and in the admin panel's Orders.

App Store purchases (untested)

Warning: not tested. The backend, the admin panel and the app contain App Store support through the same RevenueCat flow, but it has not been tested on a real iPhone or with App Store Connect. Treat it as a starting point, not a finished feature. Before you sell through the App Store, test every step below with Apple's sandbox testers, including a refund. If you only need iOS to sell courses, the web gateways (section 10) are an alternative, subject to Apple's rules for your app and country.

If you decide to try it, the steps mirror Google Play:

  1. In App Store Connect create consumable in-app purchases with the same product IDs as your Google Play products (Paid Applications agreement signed first).
  2. In RevenueCat add an App Store app with your bundle ID, connect it to App Store Connect as RevenueCat's setup asks, import the products and copy the app's public SDK key (appl_…).
  3. In the admin panel open Settings > Payments > App stores > App Store, enter the same RevenueCat secret key and webhook authorization as for Google Play plus the appl_… SDK key (environment variable REVENUECAT_APPLE_SDK_KEY), and switch it on.
  4. Add the products under Sales > Store products with the store set to App Store. The RevenueCat webhook URL is the same as for Google Play.
  5. In Xcode add the In-App Purchase capability, then test with a sandbox tester on a real device: buy, check the order in the admin panel, check the course unlocks, then refund and check access is removed.

How it stays correct

The app's word and the webhook body are never trusted: the backend reads every purchase back from RevenueCat and settles the order by the store transaction ID, so one purchase can never unlock two courses. A purchase that completes after its order was closed (for example a Play "pending" purchase paid days later) reopens the order within 7 days; otherwise it is flagged on the order for a refund from the store console.

Step 10: File storage (S3-compatible)

Uploads from the admin panel go straight to your bucket. Lumora works with Cloudflare R2, Amazon S3, Backblaze B2, MinIO and other S3-compatible services.

  • Private bucket (MEDIA_BUCKET) for lesson videos and documents. Learners get short-lived signed links (MEDIA_SIGNED_URL_SECONDS, default one hour).
  • Public bucket (PUBLIC_MEDIA_BUCKET + PUBLIC_MEDIA_BASE_URL) for course pictures, banners, logos and instructor photos. PUBLIC_MEDIA_BASE_URL is the public address of that bucket or your CDN.
  • Keys: S3_ENDPOINT, S3_REGION, S3_ACCESS_KEY_ID, S3_SECRET_ACCESS_KEY. For R2: S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com, S3_REGION=auto, S3_FORCE_PATH_STYLE=true.
  • Both buckets need a CORS rule that allows PUT from your admin panel's address, because the browser uploads directly: 
    [{ "AllowedOrigins": ["https://admin.your-domain.com"],
   "AllowedMethods": ["PUT", "GET"],
   "AllowedHeaders": ["*"] }]

Without storage you can still paste links to images and videos hosted elsewhere.

This walkthrough takes a new course from nothing to visible in the app, using only the admin panel. It assumes the backend and admin panel are running (sections 13 and 14) and the setup wizard is finished. It takes about ten minutes. The red numbers on each screenshot match the notes under it.

  1. Title: 3 to 160 characters. You can change it later.
  2. Create draft: creates the course as a Draft (learners cannot see drafts) and opens it.

Step 1: Turn on Marketplace mode

Open Settings > Business (or step 2 of the setup wizard) and click Switch to Marketplace. Only the owner can change the mode.

  1. Reason: a short note for your records.
  2. Switch to Marketplace: the app changes for every learner straight away: seller profiles and the "Become an instructor" entry can appear.

You can switch back to Academy mode later only while no other seller has a published course: unpublish or archive their courses first.

Step 2: Set the marketplace rules

After the switch, the same page shows Selling on your marketplace.

  1. Marketplace · current: the mode is on.
  2. Your commission (%): your share of each sale made by another seller, for example 20. You can give a single seller a different rate later (step 4).
  3. Seller payouts: Manual or Automatic. Either way, Lumora does not send money: you pay sellers yourself (bank transfer or another method) and record each payment in the admin panel (step 9).
  4. Instructor sign-up: Off (no new instructors), By invite only (the app shows no application form), or Open (anyone can apply from the app).
  5. Show "Become an instructor" in the app: shows the application form in the app's Account menu. Announcements per course a day limits how often a seller may message a course's learners.
  6. Save changes.

The Refund window (Settings > General, setup step 3) also matters here: a seller's share of a sale becomes payable only after that many days, so a refund can still be taken back from it.

Step 3: An instructor applies from the app

With sign-up open, a learner opens Account > Become an instructor in the app and sends a short application: display name, headline, bio, areas of expertise and links (for example a portfolio). They can apply as themselves or for an organization they run. While it is waiting they cannot send another one.

Step 4: Approve the application

Open People > Applications. Waiting applications are listed first.

  1. The applicant with their headline, email, expertise, bio and links.
  2. Approve: the person becomes a seller with a public instructor profile and gets the instructor role in the admin panel; they are told in the app. For an organization, approving creates the organization's page with the applicant as its admin. Not approved asks for a reason that the applicant sees; they may apply again later.
  1. The new seller. From here you can set a different Commission for this seller (it applies to new orders), mark them Verified, or Suspend them (new sales stop and their profile is hidden; learners keep what they bought).

With sign-up set to By invite only or Off, the app does not offer the form. An approved organization admin can add the instructors who teach for the organization from their Studio.

Step 5: The seller builds a course in the Studio

The seller signs in to the same admin panel with the email and password of their app account. (Someone who signed up with Google only sets a password first with Forgot password in the app.) They see only the Studio: their own courses, bundles, reviews, questions and earnings.

  1. New course: creates a draft, exactly as in section 15, steps 2 to 5.
  2. Their courses with each one's status.

When the course is ready, the seller clicks Send for review instead of Publish. Sellers cannot publish on their own.

  1. Send for review: the course moves to In review and appears for your team.

Step 6: Approve the course

Open Catalogue > Courses and filter by In review (the dashboard also counts courses awaiting review). Open the course and check it.

  1. Approve & publish: the course goes live in the app and can be bought.
  2. Request changes: sends it back with a note the seller sees in the Studio; they fix it and send it again.

Step 7: Sales and earnings

Learners buy a seller's course like any other. For every sale, the order item records the commission rate, your platform fee and the seller's share. Refunds are taken back from the seller's share. The seller follows their money under Earnings in the Studio:

  1. Payable now: earnings whose refund window has passed. Also shown: In refund window (not payable yet), Requested and Paid to you.
  2. Request payout: appears when something is payable.

Step 8: The seller requests a payout

  1. Amount: up to the payable balance. The amount is held until you pay or decline it.
  2. Note: where to send the money (for example a bank account) or anything your team should know.
  3. Send request.

Step 9: Pay the seller and record it

Open Sales > Payouts. Balances shows what each seller has earned, been paid and can be paid; History lists the requests.

  1. Requested: the total waiting to be paid.
  2. The request, with the seller's note.
  3. Mark paid: first send the money yourself, outside Lumora, then record it here. Not approved declines the request and returns the amount to the seller's payable balance.
  1. Transaction reference (optional): the bank or wallet transaction ID, so you can match it later. The note goes into the activity log.
  2. Record payout: the payout is marked paid and the seller is notified.

You can also record a payment to a seller without a request, from the Balances tab. A payout can never be more than the seller's payable balance.

17. API Reference

The backend in Backend/ serves one JSON API. The Flutter app and the admin panel both use it. This section covers the conventions and the most important calls. Every path below is relative to the base URL, with no extra prefix.

Conventions

  • Base URL: https://api.your-domain.com (the value of PUBLIC_API_URL).
  • Academy: send X-Tenant: acme on every request, where acme is your academy slug. Without the header the server uses DEFAULT_TENANT_SLUG; if that is empty too, the answer is 400 TENANT_REQUIRED. The demo data uses the slug demo.
  • JSON: requests and responses are JSON (Content-Type: application/json). Files never pass through the API; they are uploaded straight to storage (see File uploads).
  • Auth: signed-in calls send Authorization: Bearer <accessToken>. Catalogue reads work without a token.
  • Language: ?lang=es, else the Accept-Language header, limited to the languages the academy has switched on. Translatable text comes back in that language.
  • App version: the app sends X-App-Version. Below the minimum set in the admin panel the answer is 426 UPDATE_REQUIRED.
  • Money is always an integer in the currency's smallest unit, in fields ending in Minor (USD 2 decimals, JPY 0, KWD 3). priceMinor: 1999 in USD is $19.99.
  • Strict bodies: unknown fields are refused with 422, so send only the documented fields.
  • Rate limits: /auth/* allows AUTH_RATE_LIMIT_PER_MINUTE requests per IP (default 60). Over the limit you get 429.

The response envelope

Every successful response is wrapped like this. body holds the actual result.

{
  "success": true,
  "message": "OK",
  "body": { ... }
}

In the examples below, a line starting with → shows only the body part. Errors use the same outer shape with "success": false (see Errors). Two kinds of route skip the envelope: the payment webhooks (/webhooks/...), which answer the provider with a small plain object, and the CSV exports, which stream a file.

Pagination

Lists take ?page=1&limit=20. page starts at 1 (maximum 1000); limit is 1 to 50, default 20. A paged list returns:

{ "success": true, "message": "OK",
  "body": { "items": [ ... ], "page": 1, "limit": 20, "total": 57 } }

A few short lists (GET /instructors, GET /organizations) return a plain array when you leave out page, and the paged shape above when you send it. GET /me/learning works the same way and always adds a summary. Large admin lists may add "totalCapped": true when there are more than 10,000 rows.

Errors

Every error has a human message and a machine-readable body.code. Validation errors also carry body.fieldErrors, one message per field.

// 422: POST /auth/register with a bad email and a short password
{ "success": false,
  "message": "Validation failed",
  "body": {
    "code": "VALIDATION_ERROR",
    "fieldErrors": {
      "email": "Must be an email",
      "password": "Must be longer than or equal to 8 characters"
    } } }

// 409: the email already has an account
{ "success": false, "message": "An account with this email already exists",
  "body": { "code": "EMAIL_TAKEN" } }

// 403: a lesson behind an unfinished required lesson
{ "success": false, "message": "Finish “Welcome” to unlock this lesson",
  "body": { "code": "LESSON_LOCKED", "blockingLessonId": "uuid", "blockingLessonTitle": "Welcome" } }

Nested fields use a dot path ("sections.0.title"). Common codes: UNAUTHORIZED, FORBIDDEN, NOT_FOUND, VALIDATION_ERROR, RATE_LIMITED, INVALID_CREDENTIALS, INVALID_REFRESH_TOKEN, ACCOUNT_SUSPENDED, CODE_INVALID, CODE_EXPIRED, NOT_ENROLLED, ACCESS_EXPIRED, COUPON_INVALID, COUPON_EXPIRED, GATEWAY_UNAVAILABLE, ORDER_NOT_PAYABLE, AMOUNT_MISMATCH, FEATURE_DISABLED, MAINTENANCE, UPDATE_REQUIRED. The full list is in Backend/src/common/errors/error-codes.ts. Unexpected errors answer 500 INTERNAL_ERROR; the details go only to the server log.

Authentication

Accounts belong to one academy. A sign-in returns a session. The access token is a short-lived JWT (ACCESS_TOKEN_TTL_SECONDS, default 900). The refresh token is opaque and changes on every refresh, so always keep only the newest one.

POST /auth/register                         201
X-Tenant: acme
{ "email": "learner@example.com", "password": "a-strong-password", "fullName": "Jane Learner" }

POST /auth/login                            200
{ "email": "learner@example.com", "password": "a-strong-password" }

// both answer with a session ("message" is "Account created" for register)
{ "success": true, "message": "OK",
  "body": {
    "accessToken": "eyJhbGciOiJIUzI1NiIs...",
    "refreshToken": "q8Yt3...",
    "expiresIn": 900,
    "user": { "id": "uuid", "tenantId": "uuid", "email": "learner@example.com",
              "fullName": "Jane Learner", "roles": [], "access": {} } } }

password is 8 to 128 characters and fullName 1 to 120. A wrong email or password answers 401 INVALID_CREDENTIALS (the same answer for unknown emails). For staff, roles lists their roles (for example ["owner"]) and access maps each admin module to view or edit.

POST /auth/google                           200
{ "idToken": "<ID token from the Google Sign-In SDK>", "fullName": "Jane Learner" }
// also POST /auth/apple with the same body; both answer with a session

POST /auth/refresh                          200
{ "refreshToken": "q8Yt3..." }              // answers with a new session

POST /auth/logout                           200
{ "refreshToken": "q8Yt3..." }
→ { "success": true, "message": "Signed out", "body": { "signedOut": true } }

Google and Apple ID tokens are checked against GOOGLE_CLIENT_IDS / APPLE_CLIENT_IDS. If the provider is not set up, the answer is 501 PROVIDER_NOT_CONFIGURED. Send one refresh at a time: reusing a refresh token that was already exchanged ends that sign-in (401 INVALID_REFRESH_TOKEN).

Password reset with an emailed code takes three calls:

// 1. email a 6-digit code (same answer for unknown emails)
POST /auth/password/forgot      { "email": "learner@example.com" }
→ { "sent": true, "expiresInSec": 600, "resendInSec": 60 }

// 2. exchange the code for a reset token
POST /auth/password/verify-code { "email": "learner@example.com", "code": "482915" }
→ { "resetToken": "9f2c...", "expiresInSec": 900 }

// 3. set the new password (signs out every session)
POST /auth/password/reset       { "token": "9f2c...", "password": "a-new-password" }
→ { "reset": true }

A wrong code answers 400 CODE_INVALID (5 tries per code); an expired code answers 400 CODE_EXPIRED. Without email delivery (SMTP in the admin panel or SMTP_* in .env) step 1 answers 501 EMAIL_NOT_CONFIGURED.

Set the details and price with PATCH /console/courses/:id (for example { "priceMinor": 1999, "categoryId": "uuid", "level": "beginner" }), add the curriculum with POST /console/courses/:id/sections and POST /console/sections/:id/lessons, then publish with POST /console/courses/:id/status { "to": "published" }. Publishing a course with unfinished lessons answers 409 NOT_READY.

File uploads

Files go straight from the admin panel or app to your S3-compatible bucket with a presigned URL. The API never receives the file itself.

  1. Ask for an upload URL: POST /console/uploads with { "kind": "video", "contentType": "video/mp4", "sizeBytes": 73400320 } (kind is video or document). For images use POST /console/uploads/image with a purpose (course, banner, branding, instructor, onboarding, organization).
  2. The answer is { "mediaFileId": "uuid", "uploadUrl": "https://...", "method": "PUT", "headers": { ... }, "expiresAt": "..." }. PUT the file to uploadUrl with exactly those headers.
  3. Confirm: POST /console/uploads/:mediaFileId/complete → { "mediaFileId": "uuid", "status": "ready" } (images also return the public url). The server checks the size and type first: 409 UPLOAD_INCOMPLETE if the file is not there yet, 422 UPLOAD_MISMATCH if it differs.
  4. Attach the mediaFileId to a lesson. Only completed uploads can be attached.

Large files use the multipart routes under /console/uploads/multipart. The app uploads profile photos the same way with POST /me/avatar/upload and then PATCH /me { "avatarKey": "..." }. Without S3 settings these calls answer 501 STORAGE_NOT_CONFIGURED. Your bucket's CORS must allow PUT from the admin panel origin and expose the ETag header.

Webhooks

Payment providers call one route per provider and academy. No token and no X-Tenant header are needed: the provider's signature is the authentication, and the academy slug is in the path.

POST /webhooks/stripe/acme
POST /webhooks/flutterwave/acme
POST /webhooks/razorpay/acme
POST /webhooks/revenuecat/acme      // Google Play and App Store purchases

// answers (no envelope)
200 { "received": true }            // also for a repeated event: { "received": true, "duplicate": true }
400 { "error": "..." }              // bad or missing signature, nothing stored
404 { "error": "..." }              // unknown provider or academy

The admin panel shows the exact webhookUrl for each gateway under Settings → Payments. Stripe signs with Stripe-Signature, Flutterwave sends verif-hash, Razorpay sends X-Razorpay-Signature, and RevenueCat sends your webhookAuth value in the Authorization header. Each event is stored once and the payment is fetched again from the provider before an order is settled. POST /webhooks/bunny/acme receives Bunny Stream encoding events when adaptive video is used.

Scheduled jobs (cron)

GET /internal/cron/minute
Authorization: Bearer <CRON_SECRET>

Call this once a minute (Vercel Cron, or a system cron with curl). It closes finished exams, queues and sends push notifications, fans out campaigns and announcements, checks payments with missed webhooks, cancels unpaid orders after PENDING_ORDER_TTL_MINUTES, cleans up abandoned uploads and runs periodic cleanup. Without CRON_SECRET set, every call is refused. Like other routes it needs an academy: send X-Tenant, or set DEFAULT_TENANT_SLUG. The single steps are also available under /internal/... with the same header.

Keep CRON_SECRET, JWT_SECRET and SETTINGS_ENCRYPTION_KEY private. Never ship them inside the Flutter app or the admin panel build.

18. Database Schema

PostgreSQL 15 or newer. The backend uses plain parameterised SQL through pg, with no ORM. Business steps that touch money, progress or exams are SQL functions inside the database, so each one runs in a single transaction.

Where the schema lives

  • The full schema is in Backend/db/migrations/*.sql, numbered in the order they run. One file, 0052_legal_pages_html.js, is a JavaScript data step that runs the same way.
  • npm run db:migrate applies only the files that have not run yet, each in its own transaction, and records each file name in the schema_migrations table. Running it again is safe: it prints database is up to date.
  • When SETUP_OWNER_EMAIL and SETUP_OWNER_PASSWORD are set, db:migrate also creates your academy and its first owner account, once.
  • npm run db:seed loads Backend/db/seed.sql: the demo academy (slug demo) with 14 courses, instructors, exams, coupons and the accounts owner@demo.lumora.test and learner@demo.lumora.test (password lumora-demo-123). It refuses to run with NODE_ENV=production.
  • The migrations need the pgcrypto and pg_trgm extensions. Both are created automatically when the database user may do so. If not, run CREATE EXTENSION IF NOT EXISTS pg_trgm; once as a superuser before migrating.

Conventions

  • Primary keys are uuid with gen_random_uuid().
  • One database can host several academies. Every academy table has tenant_id referencing tenants, and every query filters by it.
  • Money columns end in _minor and are bigint in the currency's smallest unit (price_minor, total_minor, amount_minor). Currency is a 3-letter code (char(3)).
  • Dates are timestamptz (created_at, updated_at). A shared trigger, set_updated_at(), keeps updated_at current.
  • Soft delete: users, courses, lessons and coupons have a deleted_at column. Deleting a learner scrubs their personal data but keeps orders and payments as anonymous records.
  • Translatable text (category names, home section titles, FAQ, legal pages) is stored as jsonb, for example {"en": "Design", "es": "Diseño"}.
  • Allowed values are CHECK constraints on text columns, not PostgreSQL enum types.
  • Triggers keep the course counters current (lesson_count, total_duration_sec, enrollment_count, rating_avg, rating_count), refuse refunds above the amount paid, and make activity_log append-only.

How the data fits together (overview diagram)

A simplified entity-relationship view: the six main areas, their most important tables, and the columns that join one area to another. Read it before you customise anything. The full list of 92 tables follows under Tables by area.

  • A learner buys a course: users → orders → order_items (one per course) → payments (one per payment attempt) → enrollments (access to the course). A refund adds a row to refunds and ends the enrollment.
  • A learner studies: enrollments unlock the course's course_sections and lessons; each finished lesson is a row in lesson_progress; finishing the course creates a row in certificates when the course gives a certificate.
  • Quizzes and exams: a quiz lesson points at quizzes (lessons.quiz_id); each try is a quiz_attempts row. Live exams live in exams and exam_attempts, with questions from questions.
  • Who sells: every course has a seller_id. In Academy mode there is one seller, your academy. In Marketplace mode instructors and organizations get their own sellers rows; order_items.seller_id and the seller's share on each item feed payouts.
  • Many academies, one database: tenants holds each academy and its settings; every query is scoped by tenant_id.

# back up (custom format, compressed)

Do I need S3 storage?Yes for uploads from the admin panel. You can also paste https links to files hosted elsewhere.
Can the backend and admin panel run on one server?Yes. Use two nginx sites, for example api. and admin. subdomains.
Are any files minified or obfuscated?No. All three projects ship as readable source code. Third-party libraries are installed from pubspec.yaml and package.json. (The --obfuscate flag only affects the app you build yourself.)

23. Upgrading to a New Version

When a new version of Lumora is released, download it from your CodeCanyon Downloads page and read its changelog first. Your courses, learners, orders and settings live in your PostgreSQL database and your storage bucket, not in the code, so updating the code does not delete them.

Before you start

  • Back up the database (see section 18): 
    pg_dump -Fc -d lumora -f lumora-before-upgrade.dump
  • Keep your own changes in Git, or note which files you edited, so you can carry them over.
  • Never overwrite these files with the ones from the new package; they hold your settings:
    ProjectKeep your copy of
    Backend.env (above all SETTINGS_ENCRYPTION_KEY and JWT_SECRET), prod.config.js if you changed it
    Admin panel.env.local
    Flutter appconfig/app_config.json, android/app/google-services.json, ios/Runner/GoogleService-Info.plist, android/key.properties and your keystore, your package name in build.gradle.kts and MainActivity.kt, app icons, splash files, AndroidManifest.xml and Info.plist changes
  • Compare the new .env.example with your .env and add any new variables.

Carrying your own code changes forward

If you edited source files (not only settings), do not copy the new version straight over them. The safest way is Git:

# one time, before your first customisation
cd Backend            # or Admin-Panel, or Flutter-App
git init && git add -A && git commit -m "Lumora 1.0.0 original"
# ...make your changes and commit them as usual...

# when a new version arrives
git checkout -b upgrade
# copy the new package files over the folder (keep the files listed above)
git add -A && git commit -m "Lumora 1.x.x original"
git checkout main && git merge upgrade      # Git combines both; fix any conflicts it lists

Without Git, compare your old folder and the new one with a diff tool (VS Code: right-click two files > Compare Selected) and re-apply your edits to the new files.

1. Backend

cd Backend
# copy the new files over your old folder, keeping your .env
npm ci
npm run build
npm run db:migrate
pm2 restart lumora-backend
  • npm run db:migrate applies only the migration files that are new. Each file runs once and is recorded in the schema_migrations table.
  • Migrations add or change tables and columns and keep your existing rows. If a release ever needs to change existing data, its changelog says so.
  • Never edit an existing file in db/migrations/; add a new numbered file instead.
  • If something goes wrong, restore the backup with pg_restore -d lumora --clean lumora-before-upgrade.dump and go back to the old code.

2. Admin panel

cd Admin-Panel
# copy the new files over your old folder, keeping .env.local
pnpm install
pnpm build
pm2 restart lumora-admin

The admin panel stores nothing itself; all data comes from the backend. Upgrade the backend first.

3. Flutter app

  • Copy the new lib/, pubspec.yaml and assets/ over your project, then restore the files you customised (list above). If you use Git, commit first and review the diff.
  • Run: 
    flutter clean
flutter pub get
cd ios && pod install && cd ..
flutter run --dart-define-from-file=config/app_config.json
  • Raise version: in pubspec.yaml (for example 1.0.1+2) and publish the update as in section 12. Learners keep their courses and progress because these are stored on the server.
  • Old app versions keep working with the new backend unless the changelog says otherwise. To make everyone update, raise the minimum app version in the admin panel (Settings > App & maintenance).
